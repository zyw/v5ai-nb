# 会话名称命名设计方案

| 项 | 内容 |
|---|---|
| 状态 | 已实现（2026-09-19） |

## 1. 背景

### 1.1 改造前的实现

门户会话列表 `GET /api/v1/agents/{agentKey}/chat/conversations`（`ChatController.conversations`）分两步：

1. 读会话表 `v5ai_conversation`（限「本 Key + 本 Agent」，按 `updated_at` 倒序）；
2. 把**全部**会话 ID 交给 `MessageService.findFirstUserMessageByConversationIds`，
   由 `RuntimeMessageMapper.selectFirstUserMessages` 对**消息表**做 `DISTINCT ON` 查询取首条提问，
   作为未命名会话的 `preview` 展示兜底：

~~~sql
SELECT DISTINCT ON (conversation_id)
       conversation_id AS "conversationId",
       content         AS "content"
FROM v5ai_message
WHERE role = 'USER'
  AND superseded_at IS NULL
  AND conversation_id IN (...)
ORDER BY conversation_id, created_at, id
~~~

### 1.2 问题

| # | 问题 | 说明 |
|---|---|---|
| P1 | 列表接口要碰消息表 | 列表是门户首屏最高频请求，代价随 `v5ai_message` 行数增长；V39 建的部分索引（`idx_v5ai_message_conversation_active`）只能缓解，不能消除 |
| P2 | 已命名的会话也白查 | 入参是**全部**会话 ID，查出来的 `preview` 随后被 `name` 覆盖，纯属浪费 |
| P3 | `preview` 与 `name` 语义重复 | 两个字段表达同一件事（这段会话在聊什么），只是产生时机不同（读取时推导 vs 写入时固定） |

### 1.3 为什么不只在读取侧优化

- **只查未命名的会话**（`name IS NULL`）：能省掉 P2，但 P1 仍在——存量会话与「提问为空」的会话会让该查询长期存在，且列表里每多一个未命名会话就多一次消息表扫描；
- **加缓存**：引入一层缓存失效逻辑（改名、归档、新消息都要失效），复杂度不低而收益有限；
- **结论**：命名是**写入侧**的事。名字在会话产生的那一刻就已确定，就应该在那时落库；读取侧永远只读一列。

## 2. 目标与非目标

### 2.1 目标

| # | 目标 | 验收方式 |
|---|---|---|
| G1 | 会话列表只读 `v5ai_conversation` 一张表 | 列表实现里不出现任何 `v5ai_message` 查询（单测 `verifyNoInteractions(messageService)`） |
| G2 | 会话创建后 `name` 立即非空 | 建会话的 insert 语句就带 `name` |
| G3 | 名字可读 | 首轮结束后由模型改写成不超过 30 字的短标题 |
| G4 | 用户改名绝对优先 | 模型回写带 `WHERE name_source = 'AUTO'` 条件 |
| G5 | 命名不影响对话主链路 | 模型调用失败/超时/超长一律静默降级，SSE 不受影响 |

### 2.2 非目标

- 不引入分布式标题任务/消息队列（命名是单个会话的本地副作用，失败可接受）；
- 不新增「平台级小模型」配置项（标题复用该 Agent 绑定的 CHAT 模型，零配置）；
- 不做标题补偿扫描（异步任务丢失时保留兜底名即可，无需收敛机制）；
- 不把模型标题放到请求路径上（会让首字延迟 + 一次模型往返）。

## 3. 方案总览：A 兜底 + B 覆盖

| | A（规则式兜底） | B（模型标题） |
|---|---|---|
| 触发时机 | 会话**创建瞬间**（首条提问到达，`ensureConversation` 插入时） | 首轮回答**落库之后**（异步） |
| 定位 | **保底**，性能目标在 A 就已达成 | **可选覆盖**，只负责名字好看 |
| 耗时 | 0（纯字符串处理） | 一次小模型调用，异步、不阻塞 SSE |
| 失败影响 | 无 | 静默保留 A 的名字 |

> 关键点：**B 不承担任何性能目标**。读取侧（列表接口）的改动与「只有 A」时完全相同。

## 4. 详细设计

### 4.1 A：创建时兜底命名

实现：`xin.v5ai.nb.runtime.core.ConversationNaming.fromQuery`（纯函数，无 Spring 依赖）。

| 规则 | 说明 |
|---|---|
| 取首行 | 到第一个 `\n` 为止（标题要能在一行里显示） |
| 压缩空白 | 连续空白（含制表/换行）压成单个空格，再去首尾空白 |
| 截断 | 按**码点**截到 100（含省略号 `…`）：保证不超过 `VARCHAR(100)`，且不切断 emoji 的代理对 |
| 空值 | 提问为 null/全空白、或首行为空 → 返回 `null`（该会话保持未命名，门户显示「新会话」） |

| 输入 | 输出 |
|---|---|
| `帮我看看这张图\n顺便解释一下` | `帮我看看这张图` |
| `  这个   会话\t在问什么  ` | `这个 会话 在问什么` |
| `问` × 150 | `问` × 99 + `…`（共 100 码点） |
| `🙂` × 120 | `🙂` × 99 + `…`（不出现半个字符） |
| `null` / `   ` / `\n第二行才有字` | `null` |

长度常量 `ConversationNaming.MAX_NAME_LENGTH = 100` 同时被 `ChatController` 的改名校验引用，
保证「自动命名」与「用户改名」共用同一处上限定义，不会漂移。

写入点：

~~~java
// PersistingAgentRuntime.stream
var firstTurn = conversationService.ensureConversation(new ConversationDTO(
        normalizedRequest.conversationId(), normalizedRequest.agentKey(),
        normalizedRequest.apiKeyId(), normalizedRequest.userId(),
        ConversationNaming.fromQuery(normalizedRequest.query()), null, null, null));
~~~

~~~java
// RuntimeConversationServiceImpl.ensureConversation —— 只在 insert 分支采用名称
if (conversation.name() != null) {
    entity.setName(conversation.name());
    entity.setNameSource(ConversationNaming.SOURCE_AUTO);
}
baseMapper.insert(entity);
return true;             // 本次新建
~~~

返回值语义由 `void` 改为 `boolean`：**true = 本次真的新建了会话**，调用方据此决定要不要在首轮结束后排标题改写。

### 4.2 名称来源状态机：`name_source`

~~~mermaid
stateDiagram-v2
    [*] --> 未命名: 提问为空
    [*] --> AUTO: 会话创建（首条提问兜底名）
    AUTO --> AUTO: 模型标题改写（renameIfAutoNamed，仅 AUTO 命中）
    AUTO --> USER: 用户改名（PATCH /conversations/{id}）
    USER --> USER: 用户再次改名
    USER --> USER: 模型改写（WHERE 条件不命中，影响 0 行）
    note right of USER
        冻结态：任何自动命名都不再覆盖
    end note
~~~

| 值 | 含义 | 谁写 | 能否被模型改写 |
|---|---|---|---|
| `AUTO` | 系统生成（首条提问兜底名 / 模型标题） | 建会话 insert、`renameIfAutoNamed` | 能 |
| `USER` | 用户改名 | `rename`（门户 PATCH） | **不能** |
| `null` | 未命名（存量数据或提问为空） | — | 不能（`renameIfAutoNamed` 条件要求 AUTO） |

用户改名走 `updateById`（写 `name` + `nameSource=USER`）；模型回写走条件 UPDATE：

~~~java
// RuntimeConversationServiceImpl.renameIfAutoNamed
var update = new LambdaUpdateWrapper<RuntimeConversation>()
        .eq(RuntimeConversation::getId, conversationId)
        .eq(RuntimeConversation::getNameSource, ConversationNaming.SOURCE_AUTO)
        .set(RuntimeConversation::getName, name);
return baseMapper.update(null, update) > 0;
~~~

条件写在 `WHERE` 里而不是「先查后写」：**用户改名与异步标题生成可能并发，由数据库裁决，不存在竞态窗口**。

### 4.3 B：首轮结束后的模型标题改写

实现：`ConversationTitleWriter implements ConversationTitleGenerator`（端口为函数式接口，便于测试传 lambda 或 `null`）。

**触发点**：`PersistingAgentRuntime.saveAnswerOnce`（助手回答首次落库）之后调用 `generateTitleOnce`。

- 由既有的 `answerSaved` CAS 保证**只走一次**（`MESSAGE_COMPLETED` 与 `RUN_COMPLETED` 都到落库，不会排两次）；
- 停止对话（取消路径 `doOnCancel → finishCanceled → saveAnswerOnce`）同样算「首轮有结果」，那时也给会话起名；
- 只有 `firstTurn == true` 才排：**追问不改会话名**，也不白花一次模型调用。

**线程模型**：跑在 Reactor 的 `boundedElastic` 上，而不是 `@Async`。

- 本仓库没有自定义 `TaskExecutor`，`@Async` 会退化成 `SimpleAsyncTaskExecutor`——一次调用一个新线程、无上限，新会话突发时不受控；
- `boundedElastic` 是仓库里既有的阻塞调用卸载方式（`WebSearchTool` / `RagSearchTool` / `PlatformMcpTool` 同款）。

**模型来源**：复用该 Agent 绑定的 CHAT 模型，经现成的 `ModelChatClient` 端口发起一次性对话（`ModelChatClient.chatText(modelId, messages, timeout)`，Skill 的 `SkillAiGenerator`、Agent 的 `AgentScopeAgentConfigGenerator` 同款），不新造模型基础设施：

~~~java
var modelId = publishedAgentResolver.resolve(agentKey).modelId();
var messages = List.of(
        Msg.builder().role(MsgRole.SYSTEM).textContent(systemPrompt()).build(),
        Msg.builder().role(MsgRole.USER).textContent(prompt).build());
var raw = modelChatClient.chatText(modelId, messages, Duration.ofMillis(properties.getTimeoutMillis()));
var title = ConversationNaming.cleanModelTitle(raw, properties.getMaxLength());
if (title != null) {
    conversationService.renameIfAutoNamed(conversationId, title);
}
~~~

**提示词**（系统消息，长度上限取自配置）：

~~~text
你是会话命名助手。根据用户的第一句提问，生成一个简洁的会话标题，不超过 N 个字。
只输出标题本身：不要引号、不要句末标点、不要「标题：」之类的前缀、不要解释、不要换行。
使用与用户提问相同的语言。
~~~

**输入**：`ConversationNaming.questionForTitle` —— 压缩空白后截到 **500 码点**（长文提问没必要整段付费）。

**输出清洗** `cleanModelTitle`：压缩空白 → 去「标题：/title:」前缀 → 去首尾成对引号/书名号/括号 → 去句末标点 → 按码点截到配置上限；清洗后为空则返回 `null`（保留兜底名）。

**失败降级**：解析模型、调用模型、回写数据库的任何异常都在方法内吞掉，只记 `debug` 日志——兜底名已经在库里，标题只是锦上添花。

**不写用量账**：标题是平台内部行为，不记入 `v5ai_model_usage`、不影响 Agent 用量口径，也不占用会话的 `RUN_COMPLETED` 用量载荷。

### 4.4 数据模型与迁移（V40）

~~~sql
ALTER TABLE v5ai_conversation ADD COLUMN IF NOT EXISTS name_source VARCHAR(16);

-- 存量已命名的会话：V40 之前不存在自动命名，所有非空 name 都来自用户改名 → 冻结
UPDATE v5ai_conversation SET name_source = 'USER' WHERE name IS NOT NULL AND name_source IS NULL;

-- 存量未命名的会话：用首条提问回填（规则与 ConversationNaming.fromQuery 对齐）
UPDATE v5ai_conversation c
SET name = t.title, name_source = 'AUTO'
FROM (
    SELECT DISTINCT ON (m.conversation_id)
           m.conversation_id,
           left(btrim(regexp_replace(split_part(m.content, E'\n', 1), '\s+', ' ', 'g')), 100) AS title
    FROM v5ai_message m
    WHERE m.role = 'USER' AND m.superseded_at IS NULL AND m.content IS NOT NULL
    ORDER BY m.conversation_id, m.created_at, m.id
) t
WHERE c.id = t.conversation_id AND c.name IS NULL AND t.title <> '';
~~~

| 决策 | 理由 |
|---|---|
| 给存量已命名的会话打 `USER` | V40 之前不存在自动命名，非空 `name` 只可能来自用户改名；打 `AUTO` 等于允许模型覆盖用户输入 |
| 回填存量未命名的会话 | 不填的话老会话在门户里全变成「新会话」，是可见的 UX 倒退 |
| 只填 `name IS NULL` | 幂等；重复执行不会覆盖任何已有名字 |
| 回填与 Java 规则对齐 | 同一份语义（首行 / 压缩空白 / 截 100），避免新旧会话命名风格不一致 |

迁移成本：一次性 `UPDATE ... DISTINCT ON v5ai_message`，可借 V39 的部分索引；只在**部署时**执行一次，与运行期列表接口无关，建议低峰执行。

## 5. 并发与一致性

| 场景 | 结果 | 保障机制 |
|---|---|---|
| 用户在标题生成期间改名 | 用户改名生效，模型回写影响 0 行 | `renameIfAutoNamed` 的 `WHERE name_source='AUTO'` |
| `MESSAGE_COMPLETED` 与 `RUN_COMPLETED` 都到达 | 只落一条回答、只排一次标题 | `answerSaved` 的 CAS |
| 停止对话（取消） | 半截回答落库，同时给会话起名 | `doOnCancel → finishCanceled → saveAnswerOnce` |
| 追问（会话已存在） | 不改名、不排标题 | `ensureConversation` 返回 `false` |
| 「重新生成」（reuseUserMessage） | 不改名、不排标题 | 会话早已存在 → `false` |
| `resume` 续聊 | 不改名 | 同上 |
| 归档会话 | 名字照旧（归档不涉及命名） | 归档只影响列表过滤与继续对话（409） |
| 多实例部署 | 无分布式问题 | 回写是普通条件 UPDATE，指哪打哪 |
| 进程重启丢失异步任务 | 保留兜底名 | 无补偿扫描，属可接受的降级（见 §8） |

## 6. 性能

| | 改造前 | 改造后 |
|---|---|---|
| 列表 SQL 条数 | 2（会话表 + 消息表） | **1**（会话表） |
| 消息表访问 | 每次列表一次 `DISTINCT ON`，IN 列表 = 全部会话 ID | **零** |
| 复杂度 | 随会话数 × 消息量增长（索引只能缓解） | 只随会话数增长 |
| 首屏延迟构成 | 会话表查询 + 消息表查询 | 会话表查询 |
| 写入侧新增成本 | — | 建会话时一次字符串处理（纳秒级）+ 首轮结束一次异步小模型调用（可关闭） |

读取侧索引未新增：列表过滤/排序仍走 V38 的 `idx_v5ai_conversation_api_key_agent (api_key_id, agent_key)`，会话数量级小，`updated_at` 排序在内存完成即可。

## 8. 风险与取舍

| 风险 | 影响 | 缓解 |
|---|---|---|
| 每个新会话多一次模型调用 | 费用与限流压力（maxTokens ≈ 32，输入 ≤ 500 字） | 可用配置整体关闭；失败不影响任何功能 |
| 首条提问信息量低（如「继续」「你好」） | 兜底名不好看 | 正是 B 存在的理由；B 失败时接受兜底名 |
| 迁移回填成本 | 部署时一次性全表 `DISTINCT ON` | 低峰执行；只写 `name IS NULL` 的行 |
| 纯图片提问（无文字） | 会话保持未命名，门户显示「新会话」 | 刻意如此：宁可空着也不写一条无意义的名字 |
| 异步任务丢失（重启/线程池拒绝） | 该会话停留在兜底名 | 可接受：兜底名本身就是有效名称，不做补偿扫描 |
| 模型标题输出不守规矩 | 名字带引号/前缀/超长 | `cleanModelTitle` 清洗 + 码点截断 + 空值回退 |
| API 契约变更（移除 `preview`） | 外部若有消费该字段会拿到 undefined | 仓库内唯一消费方 `v5ai-ui-chat` 已同步；如需兼容，可保留字段但恒等于 `name`（本期不采用，避免留下歧义） |

### 备选方案对比

| 方案 | 性能目标 | 名字质量 | 成本 | 结论 |
|---|---|---|---|---|
| 只做 A（纯规则式） | 达成 | 截断式，长提问像半句话 | 零 | 可选，配置一键退回 |
| 只做 B（纯模型） | **不达成**（首轮结束前 `name` 为空，列表会闪「新会话」） | 好 | 每会话一次调用 + 仍需 `name_source` | 不采用 |
| **A + B（本方案）** | 达成 | 好 | A 零成本 + B 一次异步调用 | **采用** |
| B 同步放在请求路径上 | 达成 | 好 | 首字延迟 +1 次模型往返 | 不采用 |
| 平台级专用小模型 | 达成 | 好 | 需要新增配置项与管理入口 | 暂不采用，见 §9 |

## 9. 后续演进

1. ~~**平台级小模型**~~（提议的 `v5ai.chat.conversation-title.model-id` **不再需要**）：**已由 Agent 级方案取代（2026-09-21）**——标题与摘要共用一个 **Agent 级次要模型** `v5ai_agent.secondary_model_id`，未配置时回退该 Agent 绑定的对话模型；没有平台级配置项。见 `docs/次要模型与引用展示开关实现方案.md`、`docs/adr/0010-agent-secondary-model.md`。
