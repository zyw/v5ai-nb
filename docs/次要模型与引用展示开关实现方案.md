# Agent 次要模型 + 门户引用展示开关 实现方案

> **状态**：**已实现**（2026-09-21 确认两项决策：解析链**去掉**中间层全局配置；引用开关**同样作用于管理端调试页**。后端、两个前端、文档同步与 ADR 均已完成；测试覆盖情况与已知缺口见 §8）
> 关联 ADR：`docs/adr/0010-agent-secondary-model.md`（两级回退链）、`docs/adr/0011-citations-toggle-is-display-only.md`（引用开关为纯展示）
> **关联**：`docs/adr/0005-rag-call-mode.md`（同类「Agent 能力开关随快照下发」先例）、`docs/adr/0009-citations-persisted-on-assistant-message.md`（引用落库口径）、`docs/同会话短期记忆实现方案.md` §11.2（已提出「Agent 级小模型」的设想）、`docs/会话名称命名设计方案.md` §9.1（已提出标题模型配置项的设想）
> 两项需求各自独立、互不依赖，可分别交付。

## 1. 需求

### 需求一：Agent 添加「次要模型」，供会话标题与消息压缩调用

- 每个 Agent 可指定一个**次要模型**，供两处**平台内部**的模型调用使用：
  1. **会话标题改写**（首轮回答落库后异步跑一次，见 `ConversationTitleWriter`）；
  2. **会话摘要压缩**（历史窗口外的旧内容滚动压缩成一段摘要，见 `ConversationSummaryWriter`）。
- 二者**共用同一个字段**（已确认）：它们同为「轻量、非主对话」的内部调用，拆两个字段会让 Agent 表单多一个选择器、快照多一个字段，而实际诉求是「给这两种调用配个便宜模型」。
- 留空时**回退**，保证存量 Agent 行为零变化。

### 需求二：聊天窗口「是否展示 RAG 引用」开关

- 每个 Agent 可配置**门户聊天窗口是否展示引用**（助手消息下方的「引用（N 条）」折叠块）。
- 开关**放在 Agent 层**（已确认），随发布快照下发门户，由管理端决定终端用户看到什么——与既有 `webSearchEnabled`、`imageSupported` 同一条链路。

## 3. 需求一设计

### 3.1 字段与解析链

新增 `v5ai_agent.secondary_model_id BIGINT NULL`（可空）。

**次要模型解析链**（标题与摘要共用同一个解析方法）：

```
Agent.secondaryModelId              ← 本次新增，最高优先级
  ↓ 为空
Agent.modelId                       ← 主（对话）模型，最终兜底
```

**两级回退，不保留存量全局配置**（2026-09-21 决策）：原有的 `v5ai.chat.conversation-summary.model-id` 是「平台级小模型」配置，与本次「Agent 级次要模型」职责重叠且语义更弱（全局一刀切，无法按 Agent 区分）。保留它会让「这个 Agent 的摘要到底用了哪个模型」取决于一处与 Agent 相距很远的全局配置，多一层无谓的推理成本。因此**删掉该配置项**（属性字段、`application.yml.template` 注释、README 说明一并移除），配置面收敛为唯一一处：Agent 表单。

**这是有意的行为变更**：若某部署当前设置了该全局项，摘要调用将从那个模型切回「各 Agent 的次要模型（未配置则主模型）」。需在发布说明中写明（见 §11 交付顺序）。

**存量数据无需回填**：`secondary_model_id` 为 NULL 即走「回退主模型」，与删除全局项之前「未配置全局项」的存量部署行为一致。

> 与两份既有设计文档的关系：`docs/同会话短期记忆实现方案.md` §11.2 设想的「Agent 级小模型，标题与摘要共用」即本次落地；`docs/会话名称命名设计方案.md` §9.1 设想的 `conversation-title.model-id` 全局项**不再需要**（标题侧改为直接读次要模型），该设想作废。

### 3.2 解析实现

新增一个共享解析器 `v5ai-runtime/.../core/utils/AuxiliaryModel.java`（**实际落地位置**；初稿写的是 `core/model/AuxiliaryModelResolver.java`，实现时归入 `core/utils/`，与 `ConversationNaming` 等同性质的无状态工具类放在一起），两个 Writer 共用：

```java
/** 次要模型优先，未配置则回退 Agent 绑定的对话模型；两者皆空返回 null（调用方跳过）。 */
public static Long resolve(AgentDTO agent) {
    if (agent == null) return null;
    return agent.secondaryModelId() != null ? agent.secondaryModelId() : agent.modelId();
}

/** 本次解析是否命中了次要模型——只用于日志归因（这条链路不记用量、不落事件）。 */
public static boolean isSecondary(AgentDTO agent) {
    return agent != null && agent.secondaryModelId() != null;
}
```

- `ConversationTitleWriter` —— 由 `publishedAgentResolver.resolve(agentKey).modelId()` 改为调用上面的解析器。
- `ConversationSummaryWriter` —— 由 `properties.getModelId() != null ? ... : agent.modelId()` 改为调用同一个解析器。
- `ConversationSummaryProperties.modelId` 字段随之**删除**（连同 `application.yml.template` 的 `# model-id:` 注释与 README 的相关说明）。
- 现状差异需一并抹平：摘要侧本来有 `if (modelId == null) return;` 的保护，标题侧**没有** —— 主模型为空时标题会在 `chatText(null, …)` 处抛异常，被 `catch` 吞成一条 debug 日志。统一解析器后两处都补上 `modelId == null` 的空值保护（`会话 {} 的标题跳过：Agent {} 未解析出可用模型`）。
- 两处各记一条 debug 日志（`会话 {} 的标题改使用{次要|主}模型 modelId={}` / `会话 {} 的摘要使用{次要|主}模型 modelId={}`，由 `AuxiliaryModel.isSecondary` 决定措辞），因为这条调用链**不记用量、不落事件**，出问题时只能靠日志归因。

### 3.3 为什么次要模型必须是「CHAT 类型 + 已启用」

`AgentScopeModelFactory` 对模型类型**硬校验**（`:17` 拒绝非 `CHAT`）。次要模型选择器若放开到 `EMBEDDING` / `RERANK`，运行期会在 `chatText` 内抛异常，而两个 Writer 都是 **fire-and-forget 且静默失败**（`ConversationTitleWriter.java:70-72`、`ConversationSummaryWriter.java:56-59`）——表现为「标题默默没被改写、摘要默默不更新」，没有任何报错。因此：

- **前端**：选择器复用 Agent 对话模型的数据源，只列 `modelType=CHAT` 且 `enabled=true` 的模型（`AgentEditView.vue:276` 的 `listModels(..., {modelType:'CHAT', enabled:true})` 同一个调用，或 `listModelOptions(adminToken, 'CHAT')`）。
- **后端**：`AgentServiceImpl` 保存时校验 `secondaryModelId` 指向的模型存在、类型为 `CHAT`、且已启用，否则抛 `V5aiException(ErrorCode.INVALID_ARGUMENT, "次要模型不可用：需为已启用的对话（CHAT）模型，modelId=…")`（实现时用的 `INVALID_ARGUMENT`（400），与「入参不合法」的既有口径一致）。校验走跨模块端口 `ModelCatalogPort.isEnabledChatModel(Long)`（`v5ai-api` 定义、`v5ai-model` 实现、`v5ai-runtime` 已有一处同类实现可循），`AgentServiceImpl` 以 `ObjectProvider<ModelCatalogPort>` 注入 —— 端口缺席时跳过校验而不是抛异常，使纯单测与裁剪部署都不必凭空造一个模型目录。**保存时失败优于运行期静默**——这是本次设计的主要取舍点。

### 3.4 模型引用拦截必须同步扩展（易漏点）

删除／禁用模型前的引用校验只看 `model_id`：

```sql
-- V5aiModelMapper.xml:5-7 现状
SELECT COUNT(*) FROM v5ai_agent WHERE model_id = #{modelId}
```

若不同步扩展，一个只被当作**次要模型**引用的模型可以被删除/禁用而不被拦截，随后该 Agent 的标题与摘要调用开始**静默失败**（§3.3 同一个静默路径）。改为：

```sql
SELECT COUNT(*) FROM v5ai_agent
WHERE model_id = #{modelId} OR secondary_model_id = #{modelId}
```

`verifyNotReferenced` 同时服务**禁用**（`V5aiModelServiceImpl.java:192`）与**删除**（`:300-306`），一处改动覆盖两个动作，报错文案里的「N 个 Agent」计数自然包含次要模型引用。

**副作用（可接受）**：被 Agent 当作次要模型引用的模型也不能再被禁用/删除，须先解绑。这与主模型完全一致，语义正确。

### 3.5 发布快照与生效时机

- 快照 JSON 增加 `"secondaryModelId":<long|null>`（`AgentServiceImpl.snapshot`，`:243-262`）。注意这是 `formatted` **位置参数**拼接，`modelId` 用的是 `%d`——`Long` 为 `null` 时 `%d` 会输出字面量 `null` 恰好合法（既是现状，也是隐患）。新字段走 `jsonLong(Long)` 小工具输出 `null` 或数字（**已实现**），避免将来有人调换参数顺序时静默写坏 JSON。
- 解析侧 `AgentScopePublishedAgentResolver.fromSnapshot`（`:52-66`）用 `obj.getLong("secondaryModelId")`，**存量快照缺该 key 时返回 null**，正好落到回退链上——无需回填历史快照，与 ADR-0005 处理 `ragCallMode` 缺省的手法一致。
- **生效时机（与 `imageSupported` 同一个坑，必须写进文档）**：运行时走的是**发布快照**。给 Agent 换了次要模型后**必须重新发布**才生效；管理端「预览与调试」走 `resolveForDebug`，用实时编辑行，不受此限。
- 次要模型**是否随快照固化**是刻意的：固化后「线上行为 = 发布时的内容」，与 `modelId` 一致；代价是换模型要重新发布。若将来希望次要模型可热改，需要单独开一条「实时读」的通道——本次**不做**。

**「null 表示清除」——本字段与其它字段的语义不同，必须显式处理**：`updateAgent` 的其它字段沿用「null 即不改」，但次要模型是**可清除**的可选项；若也用「null 即不改」，用户一旦选了次要模型就再也回不到「复用对话模型」。因此约定：`AgentBo.secondaryModelId == null` 表示**清除**。两条支撑：

1. 前端提交的是**整个表单**、该字段恒在，不会出现「没传该字段却误清」。实现前已核对 `updateAgent` 在全仓库只有 `AgentController` 一个调用方（Java / `.vue` / `.ts` 全量检索），整体提交是这条路唯一的用法。
2. 技术上有坑：MyBatis-Plus 全局 `updateStrategy: NOT_NULL`（`common-mybatis.yml`），`updateById` **写不进 null**。故清除走单独一条语句 `AgentMapper#clearSecondaryModel(Long)`（`LambdaUpdateWrapper.set(col, null)`）。**未**采用 `@TableField(updateStrategy = ALWAYS)`：`disable()` / `publish()` 都是部分实体更新，`ALWAYS` 会让它们把该列一并抹成 NULL。

另需同步：`AgentBo`、`AgentVo`、`AgentMapper`（新增 `clearSecondaryModel`）、`AGENTS.md`/`CONTEXT.md` 术语表。

## 4. 需求二设计

### 4.1 语义界定：纯展示开关

新增 `v5ai_agent.show_citations BOOLEAN NOT NULL DEFAULT true`。

**开关只影响门户的渲染，不影响检索、协议与落库**：

| 环节 | 关闭时行为 |
|---|---|
| RAG 检索本身 | **不变**（`ragEnabled` / `ragCallMode` 是另外的开关，本项不碰） |
| SSE `RETRIEVAL` 事件 | **照常推送**（协议零变更，门户 `parseHits` 照常解析进 `citations`） |
| `v5ai_message.metadata` 落库 | **照常落库**（ADR-0009 不变量不破） |
| 历史接口返回 `citations` | **照常返回** |
| 门户「引用（N 条）」折叠块 | **不渲染** |

**为什么不做成「连落库一起停」**：引用是「这条回答当时依据了什么」的**快照**，知识库允许改手工切片、删文档、重建索引，事后**无法重建**。一旦按开关停止落库，「关 → 开」后历史引用就永久缺失，开关变成不可逆操作。同时 ADR-0009 已写明 `v5ai_message.metadata` 当前只有一个写入方（整列覆盖），多一个写入方就必须改成读-改-写 —— 为一个展示开关引入写入纪律，代价与收益不成比例。收益仅剩「历史读取每轮少 ≤8.5KB」。见 §10。

**它同时暴露了「未命中」与「未展示」不可区分的问题**，缓解办法是调试面板对 `showCitations=false` 的 Agent 给一句提示（如「该 Agent 已关闭引用展示」），避免使用者误判成 RAG 没命中。

**知识库「知识问答」tab 不受影响**：那里没有 Agent 上下文，`showCitations` 无从取值，继续用 prop 默认值 `true`。为让两份副本的行为一致，`withDefaults` 的默认值在两处都取 `true`（未传即展示，与本次改动前的行为一致）。

**prop 默认 `true` 的另一个理由**：`ChatMessageBody.vue` 有**两份独立副本**（门户 `v5ai-ui-chat/`、管理端 `v5ai-ui/`），默认 `true` 保证任何遗漏传参的调用点都退化为改动前行为，不会因为漏改一处而静默藏掉引用。

### 4.4 生效时机（两个坑，必须写进文档）

与 `CONTEXT.md` 已记录的 `imageSupported` 完全同构：

1. 门户取的是**发布快照**里的值（`PublishedAgentResolver.resolve`）→ **改完必须重新发布**，草稿态改动对线上门户不可见。
2. 门户的 bootstrap 只在**进入页面时取一次** → 发布后终端用户需**刷新页面（或重登）**才会拿到新值。

另需注意：门户 `KeyView.vue:36` 的功能清单里有「知识库引用溯源 —— 回答标注引用切片，可回查原文」。若某 Agent 关闭了引用展示，这条宣传文案对该 Agent 不再成立。属文案层的小不一致，**本次不改**（功能清单是 Key 级、开关是 Agent 级，粒度对不上），记录在案即可。

## 5. 数据库迁移

新增 **V46**（当前最新为 V45，迁移历史冻结于 V41，只增不改）：

```sql
-- V46__agent_secondary_model_and_citations.sql
-- 需求一：Agent 次要模型（会话标题改写 / 会话摘要压缩的内部调用）
--   单列引用，与 V44 之后「模型绑定为 v5ai_agent.model_id 单列」的组织方式一致。
--   可空；为空时回退为该 Agent 绑定的对话模型。
ALTER TABLE v5ai_agent ADD COLUMN IF NOT EXISTS secondary_model_id BIGINT;
COMMENT ON COLUMN v5ai_agent.secondary_model_id IS '次要模型 id（v5ai_model.id，须为 CHAT 类型且已启用）：供会话标题改写与会话摘要压缩调用；为空则回退绑定的对话模型';

-- 需求二：门户聊天窗口是否展示 RAG 引用
--   默认 true = 存量行为不变。纯展示开关：不改变检索、不改变 RETRIEVAL 事件推送、不改变引用落库。
ALTER TABLE v5ai_agent ADD COLUMN IF NOT EXISTS show_citations BOOLEAN NOT NULL DEFAULT true;
COMMENT ON COLUMN v5ai_agent.show_citations IS '门户聊天窗口是否展示 RAG 引用折叠块；默认 true；仅影响门户渲染，引用照常落库（见 docs/adr/0009）';
```

**不建外键**（与 `v5ai_knowledge_base.embedding_model_id`、`v5ai_conversation_summary.model_id` 等近期新增的模型引用列一致）：引用拦截由应用层 `verifyNotReferenced` 负责、并能给出「被 N 个 Agent 使用，无法禁用」的友好文案；建 FK 会在应用层校验漏判时抛出裸约束错误。

**存量数据**：两列都无需回填 —— `secondary_model_id` 为 NULL 走回退链，`show_citations` 由 `DEFAULT true` 补齐（存量 Agent 继续展示引用，零回归）。

迁移后按 `docs/db/dump-schema.sql` 重新生成 `docs/db/schema.md`（本项目约定，见 `AGENTS.md:193`）。

## 10. 已否决方案

**需求一**

- **仅加全局配置**（扩展 `v5ai.chat.conversation-summary.model-id`，或按 `会话名称命名设计方案.md` §9.1 新增 `conversation-title.model-id`）：否决——满足不了「每个 Agent 各配各的」。不同 Agent 的知识库与语种不同，共用一个小模型未必都合适。
- **拆成「标题模型」+「压缩模型」两个字段**：否决——两者诉求相同（轻量内部调用），拆开徒增表单与快照复杂度；将来真需要分化时再加第三个字段即可。
- **保留全局 `conversation-summary.model-id` 作为回退链中间层**（本文初稿的推荐）：**已由决策否决**——两级链语义更清晰，且该全局项与「Agent 级次要模型」职责重叠。代价是设过该项的部署会发生一次摘要模型切换，属已知的有意变更（§3.1、§9）。
- **允许选 EMBEDDING / RERANK 模型**：否决——`AgentScopeModelFactory:17` 硬校验 CHAT，运行期异常会被两个 fire-and-forget 的 Writer 静默吞掉。
- **次要模型实时读（不走快照）**：否决（本轮）——会破坏「线上行为 = 发布时的内容」这一既有不变量，且与 `modelId` 的处理方式不一致。

**需求二**

- **只做门户本地开关**（存 localStorage，同 `v5ai_chat_theme`）：否决——需求要的是 Agent 级配置；且本地开关是「用户想不想看」，而 Agent 级是「这个 Agent 对外展示什么」，两者是不同的产品决策。
- **Agent 级默认 + 门户用户可覆盖**：否决（本轮）——实现量最大（快照 + 本地覆盖 + 优先级），而本轮诉求只是「管理端能关掉这个展示」。
- **关闭时同时停止落库 / 停止推送 `RETRIEVAL`**：否决——详见 §4.1，开关会变成不可逆操作（引用是快照、事后无法重建），并为一个展示开关引入第二个 `metadata` 写入方（需改成读-改-写，见 ADR-0009）。
- **开关只作用于门户、不作用于管理端「预览与调试」**（本文初稿的推荐）：**已由决策否决**——调试页要能**当场看到**开关效果，否则验证一次要「发布 → 刷新门户」两跳。调试页走实时编辑行，天然适合预览。代价是「未命中」与「未展示」在调试页不再可区分，用提示文案缓解（§4.3）。
