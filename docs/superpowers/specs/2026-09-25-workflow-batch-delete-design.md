# 工作流批量删除设计

## 目标与边界

工作流列表支持勾选多个工作流后真正删除。仅允许删除 `DRAFT` 与 `DISABLED` 状态；`PUBLISHED` 状态必须拒绝删除。删除为物理删除，会同时清理该工作流的运行版本、运行记录和节点运行记录。当前单条 `DELETE /api/admin/workflows/{key}` 继续保持“禁用”语义，不改变现有调用方。

本次不增加数据库表或迁移，不修改既有 API 的行为，不提供单条物理删除按钮。

## API 与权限

新增管理端接口：

```http
DELETE /api/admin/workflows/batch
Content-Type: application/json

{"workflowKeys":["order-review","stock-check"]}
```

- 使用现有 `workflow:workflow:remove` 权限。
- `workflowKeys` 必须非空；服务端去除重复项并拒绝空白 Key。
- 所选 Key 必须全部存在，且状态全部为 `DRAFT` 或 `DISABLED`。任一不存在或处于其他状态，整批失败并返回明确错误，不进行部分删除。
- 若任一工作流仍有 `RUNNING` 状态的运行记录，整批拒绝；需待运行完成后再删除，避免移除正在执行中的运行数据。
- 接口成功返回统一空响应。现存 `DELETE /api/admin/workflows/{key}` 仍执行禁用。

## 服务与数据一致性

服务层以单个事务执行完整批次。先按 Key 锁定读取所有工作流行，再校验存在性与状态，以避免并发发布与删除穿插造成已发布工作流被删；随后检查是否存在 `RUNNING` 的关联运行。运行准入必须在同一事务中锁定并确认工作流行存在，再插入 `RUNNING` 运行记录；这样运行创建与删除的行锁串行化，防止运行记录在删除检查后插入。确认整个批次可删后按依赖顺序清理：

1. 查询这些工作流的全部 `v5ai_workflow_run.run_id`。
2. 按 `run_id` 删除 `v5ai_workflow_node_run`。
3. 删除对应 `v5ai_workflow_run`。
4. 删除对应 `v5ai_workflow_version`。
5. 删除 `v5ai_workflow` 主记录。

运行表及版本表当前通过 `workflow_key` 逻辑关联主表，没有主表外键级联；节点运行表通过 `run_id` 外键关联运行表。因此由服务层显式清理，并由事务保证全部成功或全部回滚。空运行集时跳过子项删除。所选数目应设合理上限（建议 100），避免超大 `IN` 参数和长事务。

## 前端交互

- 工作流表格保持受控行选择。
- 当所选项数大于 0 时，在“刷新”旁显示危险样式按钮“删除所选（N）”；没有选择时隐藏。
- 点击后打开确认框，明确说明只允许删除草稿/已禁用工作流，并且关联的运行历史、节点运行明细与发布版本会一起永久删除。
- 若所选项包含已发布工作流，后端拒绝整批操作；前端展示错误，不清空选择。成功后显示成功消息、清空选择并刷新当前列表。
- 当前列表只有 ID 在受控选择状态中；提交请求时从当前工作流数据映射到 `workflowKey`。跨页保持所选 ID 的行为沿用现状，不额外扩展选择模型。

## 测试与验收

- 服务层测试：草稿与禁用工作流可批量删除；包含已发布项时整批拒绝且不删除其他项；Key 不存在时整批拒绝；历史子表清理顺序/调用范围正确；空列表与超过上限被拒绝。
- Controller 测试：验证新接口路径、请求载体与 `workflow:workflow:remove` 权限注解。
- 前端验证：`npm run build`；确认选择后按钮显示计数，取消不触发请求，成功后清空选择并刷新，失败保留选择。
- 双数据库兼容：批量读取使用 MyBatis-Plus 参数化条件与跨方言支持的行锁语法；无需迁移。

## 已知影响

这是不可恢复的物理删除。为避免运行详情、版本查询和新建同 Key 工作流之间出现孤儿记录或历史混淆，选中工作流的所有运行数据与版本快照一并删除。已发布工作流必须先由用户禁用，之后才可删除。
