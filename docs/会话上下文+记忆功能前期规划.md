## 一、现状（两个误区对应的代码事实）

| 预期 | 当前实现 | 位置 |
|---|---|---|
| 同会话默认追加历史消息 | **被 `memoryEnabled` 门控**：开关关 → `history` 永远为空 | `AgentScopeRuntime.java:150-156`（commit `4a11425` 引入） |
| `memoryEnabled` = 跨会话记忆（同 API Key + agentKey） | **完全不存在**：没有记忆表、没有写入、没有读取；这个开关唯一的用途是上一个误区 | 全仓 grep `memoryEnabled` 只命中：Agent 字段/BO/VO/快照 + 上述门控 + UI 开关 |

即「java 会话不带历史」是双重错位：该默认生效的没生效，该跨会话的没实现。

## 四、Phase 2：跨会话记忆（新能力）

### ① 迁移 `V40__agent_memory.sql`

```sql
create table v5ai_agent_memory (
  id              bigserial primary key,
  agent_key       varchar(64) not null,
  api_key_id      bigint      not null,          -- 租户边界，对齐 ADR 0006
  conversation_id varchar(36) not null,          -- 来源会话（读取时排除当前会话）
  message_id      bigint,                        -- 来源回答的消息 id，供「重新生成」联动清理
  content         text        not null,          -- 记忆正文（截断存储）
  created_at      timestamptz not null default now()
);
create index idx_v5ai_agent_memory_scope on v5ai_agent_memory(agent_key, api_key_id, created_at desc);
```

### ② 端口与实现（沿用 `MessageService` 的端口-适配器风格）

- 端口：`v5ai-common-agentscope` 的 `core/service/AgentMemoryService`（`append` / `recent(agentKey, apiKeyId, excludeConversationId, limit)` / `deleteByAgentKey` / `deleteByMessageId`）。
- 实现：`v5ai-runtime` 的 `AgentMemory` 实体 + `AgentMemoryMapper` + `AgentMemoryServiceImpl`。

### ③ 写入 —— `PersistingAgentRuntime.saveAnswerOnce()` 之后

- 内容：`提问 + 回答`（各自截断，如各 1000 字）。
- `apiKeyId == null`（管理端调试会话）**不写**（无租户边界）。
- `reuseUserMessage == true`（重新生成）要按 `conversation_id + message_id` 覆盖写，不能追加第二条。

### ④ 读取与注入 —— `AgentScopeRuntime.withMemory()`

- 取 `recent(agentKey, apiKeyId, 当前 conversationId, K=20)`，总字符预算（如 4000）截断，拼成文本放进新字段 `AgentRunBo.memoryContext`。
- `ModelStreamTextExecutor.buildSystemPrompt()` 增加一段（与 RAG 上下文同一位置、同一口径，直连与 `HarnessAgent` 两条路径共用，自动都生效）：

```
以下是你在与该用户的其他会话中记住的内容，可作为背景参考，但不是本轮对话：
- …
```

### ⑤ 清理与联动

- `AgentCleanupMapper` 新增 `deleteAgentMemories(agentKey)`（直连 `agent_key`），并在 `AgentDeletionServiceImpl` 调用；XML 同步。
- 「重新生成」`supersedeAfter` 时同步删除被替换回答对应的记忆（按 `message_id`），避免模型记住已被作废的答案。

## 五、影响面与风险

| 风险 | 说明 | 对策 |
|---|---|---|
| token 成本上升 | 所有会话从「无历史」变「带历史」，prompt 变长、计费上升 | Phase 1 的条数/字符预算；用量估算同步修正 |
| 上下文溢出 | 超长会话直接超模型窗口 | 同上（预算兜底） |
| 存量语义变化 | `demo` 实时行 `memory_enabled=true` → 改后会真的开始跨会话记忆；旧快照（`demo` v1/v2 无该字段）解析仍为 false | 重新发布一次快照；发布说明里注明语义变更 |
| 跨 Key 串记忆 | 记忆绝不能跨 API Key | 读写都带 `api_key_id`，单测覆盖隔离 |
| 记忆膨胀 | 每轮写一条，无上限 | 保留窗口（如仅留最近 N 条 / 90 天）或按 scope 覆盖写；V1 建议「每 scope 最多 200 条，超出删最旧」 |

## 七、需要拍板的 4 个点

1. **记忆内容形态**：A) 原始「提问+回答」截断存储（零额外模型调用、可回溯、便宜，**推荐**）；B) 每轮/每 N 轮调模型提炼摘要（上下文更省，但多一次调用与费用）；C) 先 A，后续再叠 B。
2. **记忆检索方式**：A) 最近 K 条 + 字符预算（确定、简单，**推荐 V1**）；B) pgvector 向量召回（跨会话语义检索，需 embedding 配置与额外表 / 费用，可作为 V2）。
3. **同会话历史上限**：是否加、默认多少（建议 40 条 / 8000 字符，可配）。
4. **是否需要记忆管理入口**：V1 建议不做 UI（只有级联删除 + 作废联动）；如需，管理端加只读列表 + 单条/全部清空。
