# 思考随消息落库，但不回放给模型

门户在实时流里已经能折叠展示模型的思考（`REASONING_DELTA`），但它**从不落库**——刷新或重进会话，思考就消失了。我们决定把思考**持久化到所属助手消息**（`v5ai_message.reasoning`，仅助手消息有值），供门户历史回看；同时明确**不回放给模型**：思考不进上下文、不占历史窗口预算、也不进会话摘要。运行事件表（`v5ai_run_event`）保持不落思考的既有决定。这样做的理由是：回看是真实的用户诉求，而成本可控（一列 text + 取数时显式剔除）；一旦回放，思考就从"展示物"变成"上下文"，立刻牵动窗口预算、摘要口径、token 计费与合规，而平台从未跨轮回传过历史推理。

**Status**: accepted

**Considered Options**:
- **保持不落库**（原状）：不回看，思考只活在当次流式过程里；用户刷新即失。否决——这正是本次要解决的问题。
- **落库并跨轮回放**：部分推理模型在工具调用段要求/受益于回传推理内容（AgentScope 的 DeepSeek/Kimi formatter 会在同一轮的 tool 段保留 `reasoning_content`）。否决——那会让思考成为上下文的一部分，必须重新定义历史窗口的字符预算与摘要输入，并使 token 计费与合规边界随模型而异。
- **落 `v5ai_run_event`**：思考即运行事件的自然产物。否决——事件表会随思考长度膨胀，这正是原先"不落库"决定的理由；审计若真需要"某次运行的思考"，正确落点是运行侧而不是事件流。
- **落所属助手消息**（本方案）：采纳。思考是这条回答的一部分，与正文同生共死——作废、级联删除、附件归属一并复用既有机制。
- **放在独立表** `v5ai_message_reasoning`（1:1，仅按需读）：能天然避开记忆窗口的热路径 IO，但要新增表与 join。本轮否决——用"窗口/摘要取数显式剔除该列"就能拿到同样的 IO 收益，等真的出现第二个消费方向再说。

**Consequences**:
- `v5ai_message.reasoning TEXT`（可空）：`NULL` = 没有思考或历史数据；空串不表示"思考过但没内容"。
- **记忆窗口与摘要的取数必须显式剔除该列**：`findRecentByConversationId`（每轮运行都跑）与 `findActiveBetween` 用显式列清单，历史接口 `findByConversationId` 才读全文——否则每轮都会把最后一屏消息的思考读出来再丢掉。
- 门户历史接口随之返回思考；「只思考就被停止」的那一轮也要显示（前端不能再用"必须有正文或附件"来过滤）。
- 思考**无长度上限**：体积随对话轮数线性增长，属已知取舍（运行时长天然封顶），运维上需要盯这张表的体积。
- 同一批的 `v5ai_message.metadata`（text）**只建列、语义待定**：本轮没有写入方也没有读取方，迁移注释里必须写明，免得下一个人以为它是 bug。
